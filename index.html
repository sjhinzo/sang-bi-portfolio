Relational Data Architecture

Database Design & Data Model

Primary Question Answered: How is business data modeled?
3NF relational core database schema featuring surrogate primary keys, explicit foreign keys, and controlled point-in-time denormalization.

Relational ERD Structure

Parent-child relational links enforcing database integrity across all 43 tables (e.g. COMPANY → CLIENT → QUOTATION → PROJECT → ESTIMATE).

Surrogate PK `id`FK `*_id`1:N Cardinality
Header-Detail Splitting (1NF)

Separates high-level status headers from transactional line items (QUOTATION/QUOTEDETAIL, STOCKIN/STOCKIN_DE, STOCKOUT/STOCKOUT_DE) to eliminate repeating groups.

1NF CleanLine ItemsAgg Efficiency
Point-in-Time Denormalization

Stores historical item names and prices directly on transaction vouchers to preserve exact financial values even if catalog master records change later.

Historical TruthFast BI QueriesZero Join Latency
Grain & Key Strategy

Each fact table is built at a deliberately chosen grain — e.g. fact_sales_pipeline is one row per quotation, not per line item, because funnel-stage reporting doesn't need product-level detail. Business keys from the ERP (e.g. quotation_name) are kept for traceability back to source, while surrogate keys drive the join logic so a source-system ID change never breaks a report.

Grain = 1 row / quotationBusiness Key vs Surrogate Key

Governance & Roadmap

        
Governance & Recommendations

        
Primary Question Answered: Why were these technical decisions made?
Architecture rationale, data governance policies, and future improvements for enterprise scalability.

      


      

        
Architecture Rationale & Technical Decisions

        
1. Medallion Data Warehouse Architecture: Isolates raw Excel/ERP ingested tables in BigQuery staging views before executing dimensional data mart transformations, protecting downstream Power BI reports from breaking schema changes.

        
2. One Big Table (OBT) Model for Warehouse & Projects: Combining inventory status, stock-in, stock-out, and project variance into a single 20-column view (`vw_meridian_obt_dashboard`) drastically reduces Power BI DAX complexity and join overhead for real-time dashboard rendering.

        
3. Data Quality Assertions: All date parsing executes via SAFE.PARSE_DATE to handle 4 legacy date string formats without runtime ETL pipeline crashes.


        
Data Quality Checks

        
• Duplicate detection: QUALIFY ROW_NUMBER() OVER (PARTITION BY quotation_name ORDER BY quotation_created_date DESC) = 1 to collapse duplicate quotation exports before aggregation.

        
• NULL handling: COALESCE chains on every measure field so a missing value shows as 0 in a KPI, not a broken chart or a silently dropped row.

        
• Invalid / missing foreign keys: LEFT JOIN + COALESCE(m.material_name, 'Undefined') so orphaned records surface as "Undefined" in the dashboard instead of disappearing — a missing material shows up as a visible data-quality flag, not a silent gap in the total.

        
• Business rule validation: Quotations with status = '05. Stop' or 'Deleted' are explicitly excluded from funnel calculations so cancelled deals can't inflate — or deflate — the conversion rate.

SQL Naming Standards

        
base_* = cleaned staging view · fact_* / dim_* = warehouse layer · vw_* = BI-facing semantic view · snake_case throughout, no reserved words, no ambiguous abbreviations.


        
Future Improvements Roadmap

        
• Proactive KPI Alerts: Push automated threshold alerts (e.g. dead stock >90 days, project budget overrun) straight to the team instead of waiting for someone to open the dashboard.

        
• Self-Service Expansion: Extend the Power BI semantic model so Sales and Project teams can build their own report views without waiting on a request queue.

        
• Lightweight Forecasting: Add trend-line forecasting in Power BI/DAX for inventory reorder points and revenue run-rate — enough to support planning without over-engineering a full ML pipeline.
